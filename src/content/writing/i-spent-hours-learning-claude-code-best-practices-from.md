<p>A few months ago, I was using Claude the way most people do…paste some code, get an answer, paste again. Useful, sure. But also kind of exhausting. Every new conversation, I was starting from zero. Re-explaining my codebase, re-establishing context, praying Claude didn’t hallucinate an API.</p><p>Then I fell into a rabbit hole of tweets from people who’d figured out a completely different way to use it.</p><p>I also put together 9 files covering everything in this article. CLAUDE.md best practices, Skills, MCP setup, Skill Graphs, agentic workflows, learning resources, all of it. Reach out if you want them.</p><p>Also, yes, I’m part of the folk who still call it twitter and I will always call it that!</p><h3>First, the thing most people don’t realize</h3><p>When you first open Claude Code, it feels like a smarter terminal. You type things, it does things. And you can get pretty far treating it exactly like that.</p><p>But there’s a whole layer underneath that we can tend to miss: <strong>Skills</strong>.</p><p>A Skill is basically a folder that teaches Claude how to handle a specific task….repeatedly, automatically, without you re-explaining yourself every single session. You teach it once, and it just… knows. The Anthropic guide (yes, there’s a 33-page guide, we’ll get there) calls them “reusable operational assets”</p><p><strong>MCP is the kitchen. Skills are the recipes.</strong></p><p>Without Skills, you’ve got all the tools and ingredients and no idea what to make. With Skills, the right workflow just kicks in the moment you start talking about the right thing. You stop thinking about it.</p><h3>Where I actually learned this</h3><p>I want to be honest: I didn’t figure any of this out myself. I learned it from watching people share their setups on Twitter, and then I spent time organizing those tweets into something I could actually reference and use.</p><p>A lot of the best practices I found came from practitioners sharing their CLAUDE.md setups, their MCP configs, their workflow patterns.</p><h3>What a Skill actually looks like</h3><p>The structure is simpler than it sounds:</p><pre>your-skill-name/<br>  SKILL.md          &lt;- required. Core instructions + YAML frontmatter<br>  scripts/          &lt;- optional. Scripts Claude can run<br>  templates/        &lt;-optional. Output templates<br>  references/       &lt;-optional. Deep docs, only loaded when needed</pre><p>The most important part is the YAML frontmatter at the top of SKILL.md. Two fields matter most:</p><ul><li>name -lowercase, hyphens, no spaces</li><li>description -what the skill does AND the exact phrases someone would say that should trigger it</li></ul><pre>---<br>name: sprint-planning<br>description: Manages sprint planning workflows including task creation and capacity<br>  evaluation. Use when user mentions &quot;sprint&quot;, &quot;planning session&quot;, &quot;create tickets&quot;,<br>  or &quot;what should we build next&quot;.<br>context: fork<br>---</pre><p>That description field is everything. Get it right and the skill triggers exactly when you need it. Get it wrong and it just sits there doing nothing.</p><p>context: fork runs the skill in its own isolated context. Good for anything search heavy or output heavy, because it doesn&#39;t pollute your main window.</p><p>The Anthropic guide tracked some numbers on this: well structured skills reduced clarifications from 15 to 2 per workflow and cut token consumption from 12,000 to 6,000. I don’t have my own stats, but qualitatively yeah, the difference is real.</p><h3>The CLAUDE.md problem (and how to fix it)</h3><p>Before I got into Skills, I was dumping everything into CLAUDE.md. The config file that gets injected into every Claude Code session. It got long. Really long. This can slow Claude down.</p><p>This is documented and expected. A 50-line CLAUDE.md with clear architectural intent beats a 1,000-line one stuffed with “don’t do X” patches. The model has to parse through all those negations, and the important stuff gets buried. Rule of thumb: over 150 lines -&gt;rewrite from scratch. Recommended cadence is every two weeks.</p><p>The fix is <strong>lazy loading</strong>. Instead of stuffing everything in, you write things like:</p><blockquote><em>“Read API.md when touching API routes.”<br> “Read AUTH.md when dealing with authentication.”</em></blockquote><p>Claude only loads those files when it actually needs them. Context stays clean. CLAUDE.md stays short. Simple.</p><p>Two specific rules I added to my global CLAUDE.md that made an immediate difference:</p><p><strong>Bug handling:</strong></p><blockquote><em>“When I report a bug, don’t start by trying to fix it. Instead, write a test that reproduces the bug. Then have subagents try to fix it and prove it with a passing test.”</em></blockquote><p><strong>Spec-first:</strong></p><blockquote><em>“For every non-trivial code change, write a spec file first. Include impact on database structure. Update SCHEMA.md when needed.”</em></blockquote><p>Claude is noticeably faster at implementing things when a spec and DB model are directly referenced. Way less back and forth.</p><h3>Agents and subagents</h3><p>Okay this one changed things quite a bit for me.</p><p>Most of us run Claude Code in a straight line. One task, then the next, then the next. It works fine but you’re basically leaving a ton of speed on the table.</p><p>The better way: <strong>parallel subagents</strong>.</p><p>The idea is that you split work across multiple Claude instances running simultaneously, in contexts that don’t overlap with each other. This alone reportedly cuts complex project time roughly in half. The people I was learning from were very consistent on this point….don’t run linearly unless you have to.</p><p>There’s a really elegant pattern called <strong>Writer/Reviewer</strong>: one Claude writes the code, a completely fresh Claude reviews it. No shared context, no bias toward the code it just wrote. Just clean, independent eyes on the output. Because Claude is reviewing something it didn’t write, it catches things it would normally let slide on its own work.</p><p>For bugs specifically, the recommended workflow is:</p><ol><li>Write a test that reproduces the bug first</li><li>Spin up subagents to try and fix it in parallel</li><li>Accept the fix that makes the test pass</li></ol><p>You’re not just assuming the bug is fixed. You have proof.</p><p>There’s also a pattern for when you want your setup to reflect how you actually work vs. how you think you work. You run this once when setting up a new project:</p><blockquote><em>“Scrape all of my Claude sessions on this computer. Give me a breakdown of all the things I do, things worth making into skills vs plugins vs agents vs CLAUDE.md entries.”</em></blockquote><p>This surfaces patterns you didn’t know you had. It’s kind of humbling, honestly. You find out you’ve been manually doing the same five-step thing forty times when it could’ve been a skill.</p><p><strong>AGENTS.md</strong> is where you configure agent behavior so it runs without babysitting. The whole point is to frontload decisions into config rather than leaving them vague and getting interrupted constantly. Clear rules for when the agent should ask vs. when to just act.</p><p>And for code review specifically, the practitioners I followed were consistent on one thing: <strong>use multiple LLMs</strong>. Only about a third of issues overlap across different models. Running Gemini and Codex alongside Claude for local reviews, and pushing to GitHub early to get Cursor Bug Bot’s take on it, catches stuff that any single model would miss.</p><h3>Skill Graphs: when one file isn’t enough</h3><p>This is the thing Heinrich (@arscontexta) was writing about, and it’s the part that took me the longest to internalize.</p><p>His argument: a single skill file has a ceiling. It can hold one capability…a summarizer, a code reviewer, whatever. But some domains are just too interconnected for that. A therapy skill would need cognitive behavioral patterns, attachment theory, active listening, emotional regulation frameworks…you can’t fit all of that coherently in one file.</p><p>A trading skill needs risk management, market psychology, position sizing, technical analysis…all linked, all traversable, context flowing between them.</p><p>His solution is the <strong>skill graph. </strong>It’s a network of skill files connected with wikilinks. Each file is one complete thought or technique. The wikilinks between them create a traversable graph. The agent follows the relevant paths and skips what doesn’t matter.</p><p>In his words:</p><blockquote><em>“this is the difference between an agent that follows instructions and an agent that understands a domain”</em></blockquote><p>That last line is kind of the whole thing. Following instructions vs. understanding a domain.</p><p>Heinrich built the arscontexta Claude Code plugin around this …249 connected markdown files that teach the agent how to build skill graphs for you. Which is a very recursive and very satisfying solution.</p><p>I ended up building one for biomedical ML. Taking nine flat knowledge-base files and turning them into a wikilink graph that covers medical imaging, genomics, tabular clinical data, and the cross-cutting themes that connect all of them (class imbalance, evaluation metrics, SSL pretraining).</p><p>View the repo here: <a href="https://github.com/AravindKurapati/research-knowledge-vault">https://github.com/AravindKurapati/research-knowledge-vault</a></p><h3>MCP: the connectivity layer</h3><p>MCP (Model Context Protocol) is what gives Claude Code actual access to external systems…GitHub, Postgres, Figma, Jira, you name it. The config lives in one JSON file: Settings -&gt;Developer -&gt; Edit Config.</p><ul><li><strong>MCP = connectivity.</strong> Secure, standardized access to external tools and data.</li><li><strong>Skills = expertise.</strong> Domain knowledge and workflow logic on top of those connections.</li></ul><p>MCP without Skills: Claude has access but no procedural clarity -&gt; inconsistent output.<br> Skills without MCP: Claude has instructions but no live data or tools.<br> One skill can orchestrate multiple MCP servers. One MCP server can support dozens of skills.</p><p>The two worth installing first:</p><p><strong>Exa MCP: </strong>better search than Claude’s built-in. Has its own index with date filters so you’re not hitting stale training data. The get_code_context_exa tool pulls real code from GitHub/Stack Overflow/docs. Once you add &quot;For all search and research, use Exa MCP&quot; to your global CLAUDE.md, you just stop thinking about it.</p><p><strong>GitHub MCP: </strong>Claude gets direct access to your repos. Read issues, review PRs, search across repos, trigger workflows, all without leaving the terminal. Has a read-only lockdown mode so you’re not accidentally touching production.</p><p>The three questions worth asking before adding anything else:</p><ol><li>What am I copy-pasting between Claude and other tools?</li><li>What tabs do I keep switching between?</li><li>Where do I lose ten minutes every time?</li></ol><p>Every MCP should kill a specific friction point. Start with one or two, get comfortable, then expand.</p><h3>What I’m still figuring out</h3><p>The self-improving Skills pattern is the one I haven’t gotten to yet.</p><p>The idea is that skills drift as your codebase changes, a skill quietly fails when the code around it shifts, and you don’t notice until output quality visibly drops. The proposed fix is an observation loop: log each skill run, inspect failure patterns when they accumulate, propose a targeted patch, evaluate it, keep it or roll back.</p><p>But the guide is pretty clear that this is an advanced pattern. Get static Skills working first. Do periodic manual rewrites every two weeks. Only move to the observation loop when maintenance friction at scale actually becomes your bottleneck.</p><p>For now, static Skills and a clean CLAUDE.md are doing enough. I’ll get there eventually.</p><p><strong>Oh, and one more thing I just found out about….from Twitter, not from experience yet.</strong></p><p>Apparently if you’re working on a project daily and Claude is taking forever to make changes, it might be because it’s reading your entire codebase before touching anything. The fix is adding a state.md and an architecture.md alongside your CLAUDE.md</p><p>One tells Claude the current state of the project, the other tells it how everything is structured. Ryan Darani went from 8,000 tokens to 1,000 and from 8-10 minutes per change down to about 60 seconds just by doing this.</p><p>(https://x.com/SearchForRyan/status/2032574688149328103?s=20)</p><p>CLAUDE.md alone isn’t always enough. That’s the takeaway.</p><p>I haven’t tried it yet but it’s next on my list.</p><h3>The resources actually worth your time</h3><ul><li><strong>Anthropic’s official Skills guide: </strong>33 pages, free: resources.anthropic.com/hubfs/The-Complete-Guide-to-Building-Skills-for-Claude.pdf</li><li><strong>Anthropic’s agent guide</strong> : “Building Effective Agents”: anthropic.com/research/building-effective-agents</li><li><strong>Heinrich’s skill graph thread: </strong><a href="https://x.com/arscontexta/status/2023957499183829467">@arscontexta on Twitter, Feb 17 thread titled “Skill Graphs &gt; SKILL.md”</a></li><li><strong>Lilian Weng’s agent breakdown: </strong>still one of the best written explanations of how agents actually work: lilianweng.github.io/posts/2023-06-23-agent/</li></ul><p>The thing that surprised me most: none of this requires knowing how the model works under the hood. It’s mostly just file organization and writing clear descriptions. And it’s way more accessible than it looks from the outside.</p><p>Honestly, what Claude Code is capable of right now is kind of insane. And I feel like I’ve barely scratched the surface. Bigger things coming.</p>
