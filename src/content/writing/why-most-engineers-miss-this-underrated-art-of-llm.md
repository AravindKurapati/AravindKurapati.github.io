<p>I started this project in San Francisco. Being at the center of the tech world has a way of pushing you to think bigger. (But NYC is still better, sorry SF!)</p><p>Shoutout to the person who encouraged me to explore the <a href="https://arxiv.org/abs/2401.09670">DistServe paper</a>. Best suggestion I got.</p><figure><img loading="lazy" alt="" src="/writing/why-most-engineers-miss-this-underrated-art-of-llm/83020e9dd41e.png" /></figure><p>What surprised me was how little this gets discussed. I didn’t even know how important these techniques were until I dug deeper. Turns out most people optimize for throughput and ignore latency entirely.</p><p>So I decided to understand it hands-on. Started working with 2 Tesla T4s on Kaggle and started building.</p><p>What I found was eye-opening: the fundamental tension between two completely different computational phases inside LLM inference: <strong>prefill and decoding</strong>. Manage that tension correctly, and you get 10x better throughput under the same latency constraints. Miss it, and you’re stuck at 1 request/second.</p><p>This is what I learned.</p><h3>The Architecture of LLM Inference: Two Phases, Two Problems</h3><p>When you send a prompt to an LLM and get back a response, something interesting happens under the hood. The inference process isn’t one uniform computation — it’s two fundamentally different phases with completely different hardware requirements.</p><h3>Phase 1: Prefill</h3><p><strong>What happens:</strong> Your prompt (say, 500 tokens) gets processed all at once. The model computes attention over all 500 tokens in parallel to generate the first output token.</p><p><strong>Hardware requirement:</strong> This is compute-bound. Your GPU’s cores are hammering matrix multiplications. The prefill phase of a 13B LLM processing 512 input tokens can nearly saturate an A100 GPU’s compute capacity.</p><p><strong>Latency metric we care about:</strong> Time-to-First-Token (TTFT). Users care deeply about this. If they don’t see something appear on screen within 250ms, it feels frozen.</p><p><strong>The challenge:</strong> You can’t batch prefill work easily. If two requests come in with different prompt lengths, one has to wait. Longer prefills block shorter ones. This is called the <strong>convoy effect</strong>.</p><h3>Phase 2: Decoding</h3><p><strong>What happens:</strong> The model now generates one token at a time. Each new token depends on all the previous tokens (this is called auto-regressive generation). The computation per token is similar, but the batch is now distributed over many sequential steps.</p><p><strong>Hardware requirement:</strong> Memory-bandwidth-bound. The GPU spends most time waiting for data to arrive from GPU memory (HBM) than actually computing. Batching helps because you can process multiple requests together and keep cores busy while data moves.</p><p><strong>Latency metric we care about:</strong> Time-Per-Output-Token (TPOT). For document summarization, this matters more than TTFT. Users want the full output fast, not just the first token.</p><p><strong>The opportunity:</strong> Decoding is perfect for batching. 128 requests all generating their 1st token at the same time? You get great GPU utilization.</p><figure><img loading="lazy" alt="" src="/writing/why-most-engineers-miss-this-underrated-art-of-llm/6c56eb6bfcca.png" /><figcaption>Source: Perplexity Research</figcaption></figure><h3>The Coexistence Problem</h3><p>Most serving systems (including vLLM before disaggregation) colocate both phases on the same GPUs and batch them together. This seems efficient on paper: “Just maximize throughput (tokens/sec).”</p><p>But here’s what actually happens:</p><ul><li>A long prefill job arrives and starts processing.</li><li>Several short decoding jobs are waiting in the queue.</li><li>The prefill job takes 200ms to complete. In that time, the decoding jobs sit idle.</li><li>Once the prefill finishes, the decoding jobs finally start, but now they’re all competing with new prefill jobs for GPU time.</li><li>Result: Decoding jobs get longer latency than they should. TPOT suffers.</li></ul><p>Similarly, if you prioritize decoding:</p><ul><li>Prefill jobs get stuck behind decoding batches.</li><li>TTFT suffers.</li></ul><p>You can’t win. You’re constrained by whichever latency requirement is stricter.</p><h3>Enter DistServe: Disaggregation as the Answer</h3><p>The insight that changed everything came from a 2024 paper called <a href="https://arxiv.org/abs/2401.09670">DistServe</a> (from Peking University &amp; UC San Diego). Their thesis: <strong>separate the prefill and decoding phases onto different GPUs</strong>.</p><p>This is counterintuitive because:</p><ol><li>You’d think you’re wasting GPU memory by duplicating the model weights.</li><li>You’d think the communication overhead of passing KV caches between GPUs would kill performance.</li></ol><p>But the paper proved both concerns are mostly wrong. And the benefits are massive: <strong>7.4x more requests, or 12.6x tighter latency constraints</strong>.</p><p>Here’s why disaggregation works:</p><p><strong>Prefill GPUs:</strong></p><ul><li>Optimized purely for inference throughput (tokens/sec across all requests)</li><li>Use tensor parallelism to reduce execution time</li><li>Small batch sizes (prefill is compute-bound)</li><li>Goal: Minimize execution time to meet TTFT SLO</li></ul><p><strong>Decoding GPUs:</strong></p><ul><li>Optimized purely for batching and throughput</li><li>Use pipeline parallelism to scale linearly with GPUs added</li><li>Large batch sizes (perfect for memory-bandwidth saturation)</li><li>Goal: Pack as many requests as possible while meeting TPOT SLO</li></ul><p>No more compromise. Each phase gets exactly what it needs.</p><h3>The Technology Stack: What Powers Modern LLM Serving</h3><ol><li><strong>Paged Attention</strong></li></ol><p>KV caches take up a lot of GPU memory. If requests finish at different times, you get fragmentation — wasted space. vLLM treats KV cache like virtual memory: allocate in small fixed chunks, free them immediately when done, reuse them for new requests. Result: <strong>2–4x more concurrent requests</strong>.</p><p><strong>2. Continuous Batching</strong></p><p><strong>Old way:</strong> Wait for all requests in a batch to finish before starting the next batch. If one request is slow, everything waits.</p><p><strong>New way:</strong> Move requests out as soon as they’re done. Add new requests immediately. GPU always has work to do.</p><p><strong>3. Flash Attention</strong></p><p>Standard attention creates a huge matrix that wastes memory. Flash Attention computes it in smaller chunks, keeping data in fast memory instead of slow memory. Fewer data transfers = faster.</p><p><strong>4. Model Parallelism</strong></p><p>Model too big for one GPU? Split it across multiple GPUs. Two ways to do it:</p><ul><li><strong>For prefill (speed matters):</strong> Split weight matrices horizontally. Faster but more communication.</li><li><strong>For decoding (throughput matters):</strong> Split by layers. Slower per request but scales well with more GPUs.</li></ul><h3>What I Actually Built: Understanding LLM Serving</h3><p>Here’s what I did, step by step.</p><p><strong>The Goal</strong></p><p>Build a RAG app that could answer questions about FAANG companies and major US banks by reading their SEC filings. Use Llama 3.1 8B as the backbone, running on 2 Tesla T4s.</p><p>Why? Because if you can serve an LLM efficiently enough to handle real financial documents and concurrent queries, you understand the problem space. Plus, finance is a good test case — responses need to be accurate (hence citations) and fast (users hate waiting).</p><p><strong>High-Level Approach</strong></p><ol><li>Set up a baseline: Got Llama 3.1 8B running on 2 Tesla T4s using vLLM</li><li>Profiled it: Measured latency (TTFT, TPOT) to understand the baseline</li><li>Build the RAG system: Index SEC filings, create retrieval + generation pipeline</li><li>Measure concurrency: Test how it can handle multiple queries simultaneously</li></ol><p>The goal wasn’t to optimize everything right away. It was to get something working and measure the baseline so I’d know if disaggregation actually helped.</p><figure><img loading="lazy" alt="" src="/writing/why-most-engineers-miss-this-underrated-art-of-llm/ffa26ad9b75b.png" /><figcaption>output from the RAG system</figcaption></figure><p><strong>The Resources That Helped</strong></p><p>Two things made this click:</p><ol><li><a href="https://arxiv.org/abs/2401.09670"><strong>The DistServe Paper</strong></a> — Shows the math and the problem clearly</li><li><a href="https://www.youtube.com/watch?v=5ZlavKF_98U"><strong>This YouTube presentation</strong></a> — Makes the concepts visual and intuitive</li></ol><p>The paper is dense but worth reading. The presentation is a great summary if you’re short on time.</p><h3>What’s Left to Do</h3><p>Next steps are straightforward:</p><ul><li>Scale to a real SEC filings dataset (FAANG + major US banks)</li><li>Implement disaggregation (separate prefill and decoding GPUs)</li><li>Benchmark against the DistServe paper’s results</li><li>Measure actual improvement on the full workload</li></ul><p>This is still early. But the foundation is solid.</p><h3>Putting It All Together</h3><p>LLM serving isn’t magic. It’s:</p><ol><li>Understanding the two phases (prefill/decoding) and their different constraints</li><li>Using the right tools (vLLM, paged attention, continuous batching, model parallelism)</li><li>Measuring obsessively (TTFT, TPOT, throughput, SLO attainment)</li><li>Iterating on architecture (colocated → disaggregated → custom routing)</li></ol><p>I started with no GPU on my laptop. Now I have a working LLM serving system that handles concurrent requests, streams responses, and cites sources: all running on borrowed cloud GPUs.</p><p>The dream wasn’t having the fanciest hardware. The dream was understanding how to use whatever hardware I had, efficiently.</p><p>The code is open-source. The hardware is accessible. The knowledge is in papers. All that’s left is the will to try.</p><p>View my progress here — <a href="https://github.com/AravindKurapati/llm-serving-sec-filings">https://github.com/AravindKurapati/llm-serving-sec-filings</a></p><p>Now go build something.</p>
