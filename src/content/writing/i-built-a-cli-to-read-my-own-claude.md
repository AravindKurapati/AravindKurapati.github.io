<p>Sometime in March I sat down on a rather quite Friday night on <em>Long Island</em> to figure out what I’d worked on that week.</p><p>I knew I’d opened Claude Code in about five different project folders and had a vague memory of fixing something in the Modal vLLM endpoint. Nothing past that.</p><figure><img loading="lazy" alt="" src="/writing/i-built-a-cli-to-read-my-own-claude/bd1ed3c5c3db.png" /></figure><p>The annoying part is that all of it was already on my laptop. <code>~/.claude/projects/</code> had something like 230 session files at that point, one JSONL per session, every prompt and tool call and shell command and error and token count sitting there in a perfectly readable format.</p><p>The agent had been keeping a crazy (the good kind!) log of my work the whole time. I didn’t even know it existed.</p><p>So I worked on a thing that does:</p><h3>What it does</h3><p><code>agent-flight-recorder</code> reads the JSONL files Claude Code and Codex already write, parses them and dumps everything into one SQLite database at <code>~/.afr/afr.db</code>. From there I can query the thing.</p><p>For each session it pulls:</p><ul><li>the first user message (treated as the goal)</li><li>every tool call, with input summary and success/error</li><li>every shell command, with exit code and a stdout/stderr excerpt</li><li>every file read, write, patch, delete</li><li>failed tool calls and non-zero shell exits</li><li>input/output/cache token counts</li><li>an outcome tag I add later: <code>shipped</code>, <code>blocked</code>, <code>abandoned</code>, <code>exploratory</code></li></ul><p>API keys, bearer tokens, private keys and <code>.env</code> contents are redacted before they hit the database. No info leaves the machine.</p><p>You can ingest manually:</p><pre><code>afr ingest claude
afr ingest codex</code></pre><p>Or wire a <code>Stop</code> hook into <code>~/.claude/settings.json</code> so it runs automatically the moment a session closes.</p><figure><img loading="lazy" alt="" src="/writing/i-built-a-cli-to-read-my-own-claude/09d4ca6f92dc.png" /></figure><h3>Using it</h3><pre><code>afr list-days 7
afr search “modal deployment”
afr stats-days 30
afr export 50c3f2a1-out report.md</code></pre><p><code>afr list</code> is the one I keep open. It’s a flat table: session id, goal, outcome, tokens, date. The first time I ran it across a month, I found seven separate sessions with some variation of “fix the modal deployment.” Four blocked, two abandoned, one shipped. If I’d seen that table in week two instead of week five I’d have stopped poking at it and gone and read the Modal docs.</p><p><code>afr search</code> is the one I open when I get déjà vu. Full text across goals and summaries, with -days` to scope. It replaces the “have I done this before” of opening a new Claude session and re-explaining the project context. (and wasting 2k tokens for it!!0</p><h3>Why SQLite</h3><p>I had a friend ask why I didn’t make this a hosted thing. Two reasons. One, my JSONL files include prototype code for things I haven’t talked about publicly and at least a few prompts I’d rather not have sitting on someone else’s server, redactor or no redactor. Two, SQLite is the most boring possible substrate, which is perfect for this: single file, WAL mode, backs up by copy, queryable from any language and if I stop maintaining the CLI tomorrow the data is still readable with <code>sqlite3 ~/.afr/afr.db</code>.</p><p>The CLI is small. Eight commands. No TUI, no web UI, no slop dashboards. Just commands you’d type.</p><p>So essential the CLI made it harder to lie to myself about my own work!</p><p>If <code>~/.claude/projects/</code> on your machine has more than a couple dozen files in it, the data is already there. Almost nothing else does anything with it.</p><p><strong><strong>Repo:</strong></strong> <a href="https://github.com/AravindKurapati/agent-flight-recorder">github.com/AravindKurapati/agent-flight-recorder</a></p>
